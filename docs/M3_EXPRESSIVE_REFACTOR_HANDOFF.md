## 1. 委派目标与执行边界

将本项目整个前端统一为 **Material 3 Expressive 设计语言，整体简约、操作高效**。用户提供的控件样例用于确定控件造型与交互语言，不用于照搬业务页面布局。

按两个阶段实施：

1. **先完成创作工作台 `/`**，建立可实际交互的视觉基准。共用主题、导航和控件允许同步影响图库。
2. **停下等待用户确认**。只有用户明确接受工作台基准并允许继续，才能推进我的图库 `/gallery` 的专属布局与控件改造。

本轮用户明确要求“不要自己实现，创建一个工作委派文档”。因此，文档的创建不代表已经开始开发，也不代表允许后台自动执行后续阶段。接收方获得后续实现委派后，仍须先处理第 3 节的未决事项，并遵守试点验收门禁。

目标是本仓库的 Web 应用，不是承载编码代理的聊天 GUI。

## 5. 必须守住的业务行为

### 5.1 参数、协议与配置

- 保留 OpenAI-Compatible、Gemini-Compatible、自定义 Base URL、模型选择与自定义模型 ID。
- 模型能力联动、非法参数回退和旧配置兼容继续使用现有逻辑。不要在新控件里另写一套参数规则。
- 保留全部现有参数及条件显示，包括尺寸/比例、自定义宽高、数量、质量、格式、背景、压缩、审核，以及 Gemini 的分辨率、思考深度、仅输出图片等。
- 保留协议/模型决定的禁用状态及说明，例如不支持透明背景的组合、有参考图时的审核限制。
- 保留 API Key 显隐、配置自动保存及密钥风险提示。折叠设置不能让未配置用户找不到入口。
- 主题存储不能覆盖现有配置键；不迁移、不清空用户配置和提示词。

### 5.2 参考图

- 保留上传、拖放、批量添加、缩略图、逐张移除和键盘选择文件。
- 保留按协议/模型联动的格式、张数和体积限制；读取中、超限时不能错误开放提交。
- 切换模型导致超限时，保留图片与错误说明，不擅自删图。
- 保持窗口级拖放保护，避免浏览器直接打开拖入文件。
- 不把原图 Base64 放入 localStorage、日志、请求预览或交付截图。

### 5.3 提交、恢复与防重复计费

- 初次任务发现未完成、连接异常或存在待确认提交时，保留现有提交门槛。
- 网络中断后的“待确认”不等于生成失败。保留查询、说明及恢复入口。
- 重试继续使用同一任务 ID 与冻结的原请求；不得为了简化按钮逻辑创建第二个付费任务。
- 提交尚未确认时保留离页提醒；后端已确认接收后，刷新或切换页面不取消任务。
- 排队、生成中、成功、失败、连接错误、删除错误等状态继续来源于现有逻辑，不伪造进度百分比。
- 主题切换、折叠设置和响应式变化不能清空草稿、参考图、选中任务或触发提交。

### 5.4 结果、历史与删除

- 结果画面与选中的任务必须对应；任务选中态应明确，不能只显示“最近一张图”代替当前选择。
- 保留请求尺寸与实际原图尺寸的区别、尺寸不一致提示和原始文件下载语义。
- 不为适配卡片而修改实际图片字节，不自动裁剪、拉伸、放大或重发请求。
- “清空结果”不等于删除任务；“删除任务”不等于取消生成，文字与确认机制不能混用。
- 排队/生成中的任务仍不可删除；删除终态任务会删除其相关图片的行为不变。
- 图库删除后端图片可能按整个任务联动删除多张图片；保留实际影响范围提示和确认，不改成看似只删一张的交互。
- 保留旧浏览器图库与后端图库的来源区别，不进行数据迁移或清理。

## 6. 视觉与组件工作要求

### 6.1 全局设计基础

**颜色**

- 保留暖金身份，以现有色阶为起点建立深浅两套语义角色。
- 组件只引用角色，如主色、容器、正文、次级文字、描边、错误；不要在各组件散落新的金色或蓝色色值。
- 后续换蓝色时，应主要修改集中色板及角色映射，不逐页替换颜色。无需新增用户调色器、动态取色或多套品牌配置功能。
- 浅色不是深色的简单反相，也不能直接把深色的亮金用于白底正文。正文、按钮文字、错误、禁用、焦点和选择态都需分别检查。
- 新旧页面与菜单、弹窗等浮层都要跟随同一主题；排查局部硬编码背景和白色文字。

**排版与空间**

- 优先沿用现有字体、中文回退与 SVG 图标。标题、正文、辅助说明、参数值分别明确层级，不另加装饰性字体。
- 主内容是生成操作与图片，不是宣传式大标题。收紧重复说明和装饰性空白，但保留关键安全提示。
- 统一控件、菜单、卡片的圆角等级；不要把所有容器都变成胶囊。
- 用容器层级、间距和少量分隔组织信息，避免卡片层层嵌套、过多描边、发光和大面积装饰渐变。
- 对照布局若获批，其特点应是输入与当前结果容易对应，而不是新增无业务含义的装饰。

**动效**

- 使用短促的状态反馈、菜单进出、箭头和选择标记变化。保留样例语言，降低整体动效存在感。
- 不引入滚动劫持、整页模糊入场或妨碍连续操作的动画队列。
- 尊重 `prefers-reduced-motion`；关闭或缩短非必要动效后，所有操作仍可理解。

### 6.2 共用组件

| 控件族 | 具体工作 | 完成标准 |
| --- | --- | --- |
| 单选下拉 | 实现可复用的 React 受控选择控件，逐一接入现有选择器 | 保留值、标签、禁用项、事件回调和参数联动；不再依赖样例的直接 DOM 修改 |
| 按钮 | 统一主要、次要、文本、图标、危险操作的层级 | hover、focus、pressed、disabled、busy 都可辨识；不混淆生成与删除 |
| 文本输入 | 统一单行、多行、数字、密钥字段与字段说明 | 标签可见、错误关联明确、中文输入可用；不因布局变化丢焦点或内容 |
| 分段控件 / chips | 统一导航、协议选择、灵感入口的状态反馈 | 导航仍是导航、选项仍是选项，不能为了外观改变交互语义 |
| 上传区 | 统一空态、拖入态、读取态、已选择与错误态 | 限额与禁用原因可见，删除单张参考图不会触发提交 |
| 结果与任务 | 统一状态标签、容器、骨架、空态、错误与操作区 | 当前结果与所选任务对应；关键错误及恢复入口不会被装饰隐藏 |
| 浮层 / 弹窗 | 统一背景、圆角、阴影、遮罩与焦点样式 | 不被父容器裁切，不躲在 sticky 页头后面，窄屏可操作 |

优先抽取真正重复的控件。不要为了这次重构建立一个大型通用设计系统，也不要顺手迁移状态管理、路由或整个 CSS 技术栈。若确实需要新依赖，应先解释必要性、体积和替代方案。

### 6.3 自定义下拉的专项要求

- 正确关联字段标签、触发器、列表与选项；区分“键盘活动选项”和“已提交选择”。
- 按控件所用的可访问模式实现焦点：方向键导航，Enter/Space 确认，Escape 取消并合理回焦，Tab 离开不困住用户；Home/End 与长列表定位一并考虑。
- 读屏能获知展开状态、选中项及活动项；不能只有外观上移动高亮。
- 点击外部关闭，点击禁用项不生效；关闭菜单不能意外更改参数。
- 长列表有最大高度并可滚动，键盘活动项保持可见；长模型名不挤坏布局。
- 处理视口边缘、滚动容器、缩放与层级；根据实际结构选用浮层挂载或其他合理方案，不机械复制绝对定位。
- 多个实例彼此独立，清理事件监听，避免一个全局键盘事件同时控制多个菜单。
- 深浅主题、触屏与减少动效模式下保持相同操作语义。

## 8. 验证与验收

### 8.1 验证原则

- 本文档交付不运行测试或构建；以下是接收方未来实施时的要求。
- 以变更风险决定验证范围，不默认跑全仓库、后端或完整端到端测试。
- 未经许可，不得调用真实收费图片生成接口；不使用真实密钥和私密图片作为公开截图材料。
- 优先使用现有测试、可控测试数据和隔离的模拟环境；不得清空或修改真实任务数据来制造空态。
- 已有前端测试针对提交/恢复服务，其通过不代表新控件的键盘、主题和视觉已验证。

### 8.2 建议检查矩阵

| 范围 | 至少覆盖 | 验收要求 |
| --- | --- | --- |
| 主题 | 深色、浅色；若采用系统模式，再测系统变化、手动覆盖、刷新 | 两页及浮层一致；无不可读文字；切换不丢草稿和任务选择 |
| 桌面 | 建议 1440×900、1280×800 | 核心操作层级清楚，没有为装饰留白挤出主要内容 |
| 窄屏 | 建议 768×1024、390×844，并检查 320px 宽 | 无非预期整页横向滚动；关键功能完整；菜单和弹窗不出屏 |
| 下拉 | 鼠标、触屏、纯键盘、长选项、禁用项、多个实例 | 选择正确、焦点可见、Esc/Tab 正常、无裁切和串扰 |
| 表单 | 两种协议、不同模型、自定义 ID、条件参数 | 值与禁用条件正确，切换控件不改变原参数规则 |
| 上传 | 空态、读取中、已上传、移除、格式/限额错误、切模型超限 | 原图片保留，原因明确，提交门槛与现有逻辑一致 |
| 提交恢复 | 未配置、发现中、连接异常、提交中、待确认及重试 | 引导和恢复入口可见；不产生第二个任务 ID；离页保护不丢失 |
| 结果与历史 | 排队、生成中、成功、多图、失败、切换任务、清空与删除 | 状态与选中任务一致；清空、删除、不可删除状态可区分 |
| 图库连带影响 | 两主题、导航、卡片文字和预览浮层 | 第一阶段共用改动不造成不可读或无法操作 |
| 可访问性 | 键盘路径、可访问名称、读屏状态、减少动效 | 焦点不丢失、不被遮挡；状态不只靠颜色；必要信息不会仅短暂出现 |

普通正文对比度以至少 4.5:1、大号文字及关键非文本界面元素以至少 3:1 为目标；禁用与辅助内容也需保持合理可辨性。触控目标应有足够面积，紧凑不能变成难以点中。

### 8.3 命令与范围

运行时改动完成后，前端构建可使用根目录已有命令：

```sh
npm run build:web
```

它包含 Web TypeScript 构建检查与 Vite 构建，不要求同时构建后端。lint 优先只检查修改的文件，不把全仓修复混入任务。

若修改触及提交事件接线、服务调用或恢复相关行为，运行现有相关测试：

```sh
npm run test:web
```

若新增测试文件，确认测试入口确实执行了它；现有 Web test 脚本只显式运行一份提交服务测试。必要时运行 Web 自身的类型检查以覆盖测试类型，不以重复的全仓检查代替针对性验证。

对于新主题偏好解析、自定义选择器键盘状态等非平凡逻辑，补充最小而有效的验证；优先复用现有工具。不要只为改了样式就新建冗余测试，也不要为验证明显变化创建临时测试脚本。

若浏览器自动化或读屏环境不可用，交付中明确标注未覆盖项，提供人工验收步骤；不能仅凭构建通过宣布视觉与可访问性全部通过。
